# Plugin Package Rules

These rules apply to every package under `plugins/`.
Normative keywords follow BCP 14.

## Package Layout

- Each plugin MUST live directly under `plugins/<plugin>/`.
- Each published plugin MUST include `README.md` and `.claude-plugin/plugin.json` at its plugin root.
- Runtime files, scripts, templates, and packaged assets MUST stay inside the owning plugin root.
- Each plugin README MUST describe purpose, included skills and agents, runtime model, layout, and scope notes.
- Ignored generated byproducts SHOULD remain untouched unless tracked, validation-breaking, or hiding a source problem.

## Versioning

Git-sourced Sinon plugins SHOULD omit plugin and marketplace-entry `version` fields unless maintainers adopt a semver release cycle.
Without `version`, Claude Code uses the source commit SHA as the update key.
If maintainers set `version`, they MUST bump it for every release users should receive.

## Claude Plugin Manifest

`.claude-plugin/plugin.json` MUST:

- use `$schema: "https://json.schemastore.org/claude-code-plugin-manifest.json"`
- use object-form `author`
- omit `interface`
- keep every declared path inside the plugin root and prefixed with `./`

Default component locations SHOULD remain undeclared because Claude Code discovers them automatically:

- `skills/`
- `agents/`
- `hooks/hooks.json`
- `.mcp.json`
- `.lsp.json`
- `settings.json`
- `output-styles/`
- `themes/`
- `monitors/monitors.json`
- executable `bin/`

Use manifest component fields only for custom paths or supported inline configuration.
Custom directory paths SHOULD use trailing-slash form.
A replacing component field MUST preserve an existing default path or remove the unused default directory.

## Agent Package Surface

- Plugins with agents MUST use a direct `agents/<kebab-name>.md` layout.
- Filename stem and frontmatter `name` MUST match exactly.
- Nested files under `agents/` are prohibited because recursive discovery can register unintended agents.
- Agent model, effort, topology, counterpart, and tool rules live in `agent-capability-kit/AGENTS.md`.
- Optional per-agent depth belongs in a reusable skill or `docs/agent-references/<agent>/`, never below `agents/`.

## Agent Skill Surface

Agent Skills follow the agentskills.io loading model:

1. `description` is the activation trigger.
2. `SKILL.md` is the self-sufficient ordinary path.
3. `references/`, `assets/`, and `scripts/` provide on-demand additive depth.

When creating, editing, reviewing, validating, or packaging a skill, load `plugins/agent-capability-kit/skills/skill-authoring/SKILL.md`.
Detailed portable schema and placement rules live in `agent-capability-kit/AGENTS.md`.

## Documentation Style

- Markdown SHOULD prefer headings, lists, tables, and code blocks over dense prose.
- Headings MUST be in English unless an existing document intentionally uses another language.
- Heading levels MUST increase sequentially and have a blank line after each heading.
- Fenced code blocks MUST specify a language and have a blank line before the fence.
- Nested fences MUST use a longer outer fence.
- Tables MUST use `| --- | --- |` separator cells.
- Unicode box-drawing characters are prohibited; use ASCII tree markers such as `+--` and `|`.
- Normative rules documents MUST use BCP 14 language.
- Example code comments MUST use the language's documentation-comment style.
- Blank lines MUST NOT appear inside example functions or methods.
- Example code SHOULD import declarations instead of using fully qualified names.
- Version-sensitive commands, APIs, and configuration MUST be verified against authoritative sources.
- A modified review surface MUST receive follow-up review.

## YAML Style

- Use plain or double-quoted scalars for short readable strings.
- Use folded `>-` only for one long logical string that needs physical wrapping.
- Use literal `|-` only when line breaks are semantic.
- Identifier-like booleans, numbers, tokens, and whitespace-free paths MAY remain plain.

## POSIX Shell

Every POSIX shell script MUST begin exactly with:

```sh
#!/usr/bin/env sh
# -*- coding: utf-8 -*-
set -e
```

Shell scripts:

- MUST NOT use `set -u`, `set -eu`, `set -ue`, or `set -euo pipefail`
- MUST NOT use `[[ ]]` or `=~`
- MUST use `[ ]` only as an `if`, `elif`, `while`, or `until` predicate
- MUST use `grep -qE` for regular-expression matching
- MUST NOT redirect output to `/dev/null`
- MUST NOT suppress failures with `|| true`
- MUST use uppercase constants and lowercase variables
- MUST NOT contain blank lines inside function bodies
- MUST use JSDoc-style function and constant docstrings, with a blank `#` separator before tags

Canonical function shape:

```sh
# Ensure the given path exists.
#
# @param path Filesystem path to check.
# @return Returns 1 when the path is missing.
ensure_path() {
    path="$1"
    if [ ! -e "$path" ]; then
        echo "error: '$path' not found" >&2
        return 1
    fi
}
```

## Single-File Runtime Scripts

Prefer inline dependency declarations:

- Python: PEP 723 metadata and a `uv run` shebang
- Deno: versioned `npm:` imports
- Bun: direct versioned npm imports
- Ruby: Bundler inline gemfiles

Do not introduce a project-level dependency for one isolated script when the runtime supports inline declarations.

## Source Modification

Use a language-appropriate AST, PSI, or structured parser when reasonably available.
Regex or string surgery is a last resort and is allowed only when no robust parser exists, the change is purely lexical, or the file is too small for parser overhead.
When using string-based editing, identify the exact declaration or node being changed.

## Review and Validation

Reviewers MUST check:

- package and manifest alignment
- README inventory parity
- agent and skill self-sufficiency
- progressive disclosure and blocker-based references
- workflow, example, path, and output consistency
- hook, command, filesystem, network, credential, and publication risks

Run `claude plugin validate <plugin-root>` for each changed plugin.
Repository package validation runs through `plugins/harness/scripts/plugin-self-check.ts` and `bun run check`.
