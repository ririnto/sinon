# Repository Guidelines

This file applies to `plugins/`. Closer plugin instructions override it. Each publishable package lives directly under `plugins/<plugin>/` and keeps its README, manifest, runtime files, scripts, and assets inside that root.

## Project Structure

Use the plugin README for its layout and supported runtime components. Open `agent-capability-kit/AGENTS.md` when changing agents or skills, and the owning plugin `AGENTS.md` for package-specific checks.

## Build, Test, and Development Commands

Run `claude plugin validate plugins/<plugin>` after changing that package. Run `bun run check` before an integrated handoff. Harness changes also require `plugins/harness/scripts/plugin-self-check.ts`.

## Coding Style and Testing

Keep manifests schema-valid, use object-form authors, and keep declared paths inside the plugin root. Keep default runtime locations undeclared unless a custom location is required. Write English headings, language-tagged code fences, and BCP 14 terms in stable rules. Follow the owning skill for portable Agent Skill structure.

## Commit and Publication

Stage only the affected package. Do not add generated byproducts unless they are tracked or required for validation. The top-level session owns commits and publication; package agents remain leaves.

## Security and Configuration

Review hooks, MCP, LSP, settings, scripts, and packaged assets for filesystem, command, network, credential, and publication effects. Open the package README when you need its component inventory.

## Scope and Precedence

Do not copy package detail into this file. A plugin-local `AGENTS.md`, its README, and the owning `SKILL.md` provide the authoritative detail for that package. Stop when those sources disagree and report the conflicting paths.
